## Detailed Test Cases

### TC-1 – Request reset link with valid registered email

- **ID:** TC-1  
- **Title:** Request reset link with valid registered email  
- **Linked AC:** User can request a reset link by entering their registered email  
- **Type:** positive  
- **Priority:** high  

**Preconditions**  
User has an existing active account with a verified email address stored in the system.

**Test Data**  
- Registered email: `user@example.com` (or equivalent valid, verified account in test env)

**Steps**
1. Open a web browser and navigate to the application's login page.
2. Click on the "Forgot password" link or button on the login page.
3. In the "Email" input field, enter a valid email address that is registered and verified in the system (e.g., `user@example.com`).
4. Click the "Send reset link" button.
5. Check the inbox of the entered email account.
6. Locate the email from the application containing the password reset link.

**Expected Result**
- The system displays a confirmation message indicating that, if the email exists, a reset link has been sent.  
- A password reset email containing a unique reset link is delivered to the specified registered email address.

**Assumptions / Notes**
- Email delivery infrastructure (SMTP or email service provider) is operational and configured for the test environment.  
- Tester has access to the mailbox of the registered email address used in the test.  
- System may use a generic confirmation message to prevent account enumeration; the test remains valid regardless of message wording as long as the email is actually sent.

### TC-5 – Reset link expires after 30 minutes

- **ID:** TC-5  
- **Title:** Reset link expires after 30 minutes  
- **Linked AC:** Reset link is valid for 30 minutes only  
- **Type:** edge  
- **Priority:** medium  

**Preconditions**  
User has requested a password reset, and a reset link email has been received in the user's inbox.

**Test Data**  
- Valid reset link (timestamp known at time of issuance)

**Steps**
1. Open the received password reset email and note the timestamp when the email was received.
2. Wait until at least 31 minutes have elapsed since the email receipt time (or the token issuance time if displayed).
3. Click the password reset link in the email after 31 minutes have elapsed.
4. Observe the page or message displayed by the application.

**Expected Result**
- The system displays a clear message that the reset link has expired.  
- The system does not allow the user to proceed to set a new password.  
- No password change occurs.

**Assumptions / Notes**
- The 30-minute validity is measured from the time the link/token is generated, which is approximately the email sent time.  
- Application clock and test environment clock are synchronized sufficiently for this test.  
- No grace period beyond 30 minutes is configured; if there is, acceptance criteria should be updated.

### TC-6 – Reset link used within 30 minutes is accepted

- **ID:** TC-6  
- **Title:** Reset link used within 30 minutes is accepted  
- **Linked AC:** Reset link is valid for 30 minutes only  
- **Type:** positive  
- **Priority:** high  

**Preconditions**  
User has requested a password reset and received a reset email within the last 10 minutes.

**Test Data**  
- Valid reset link (issued within 30 minutes)  
- New password that satisfies password policy

**Steps**
1. Open the password reset email that was received less than 30 minutes ago.
2. Click on the reset link in the email.
3. Observe the application behavior after following the link.
4. Enter a new valid password in the "New password" field that meets the system's password policy.
5. Confirm the new password in the "Confirm password" field, matching the previously entered password.
6. Submit the password reset form.
7. Attempt to log in using the updated password and the user's email/username.

**Expected Result**
- The reset link opens a password reset page without any error.  
- The new password is accepted and confirmation succeeds.  
- Login with the new password is successful.  
- Login with the old password no longer works.

**Assumptions / Notes**
- Password policy (length, complexity) is known and adhered to in the test data.  
- Any existing sessions may either be invalidated or remain as per security policy; this test focuses on successful password change and login.

- **Priority:** medium

- Updated (new) password from the successful reset

**Steps**

2. After successful password reset, navigate back to the email containing the same reset link.
3. Click the same reset link again.
4. Observe the application behavior and any messages displayed.

**Expected Result**
- The system does not allow reuse of the same reset link.  
- An appropriate message is displayed indicating that the link has already been used or is invalid.  
- No further password changes are allowed via this link.

**Assumptions / Notes**
- Security design requires one-time use of reset tokens; if multi-use is allowed within validity period, this behavior must be clarified.  
- Any error or info message presented should not reveal sensitive internal details (e.g., exact token state).

- Exact wording of error message may vary; any clear mismatch indication is acceptable.

### TC-10 – Password reset with password not meeting policy requirements

- **Linked AC:** User can set a new password via the reset link

5. Observe validation messages and whether the reset succeeds.

- The user's password is not updated.

**Assumptions / Notes**

- Message content does not leak sensitive policy details beyond what is acceptable by security standards.

### TC-12 – Password reset attempt using tampered or malformed reset token

- **ID:** TC-12  
- **Title:** Password reset attempt using tampered or malformed reset token  
- **Linked AC:** User can set a new password via the reset link  
- **Type:** negative  
- **Priority:** medium  

**Preconditions**  
User has received a valid reset link email, and the link contains a reset token parameter in the URL.

**Test Data**  
- Valid reset link URL (copyable/editable)  
- Tampered token value (randomized or modified)

**Steps**
1. Open the password reset email and right-click on the reset link to copy the link URL.
2. Paste the reset URL into a text editor.
3. Identify the reset token or query parameter in the URL (e.g., `token=...`).
4. Modify the token value to a different random string or alter part of the token (e.g., change some characters).
5. Paste the tampered URL into the browser's address bar and navigate to it.
6. Observe the behavior and display when accessing the reset page with the invalid token.

**Expected Result**
- The system detects the invalid or tampered token.  
- The system does not display a functional password reset form.  
- An error message is shown indicating the link is invalid or expired.  
- No password change is possible with the tampered link.

**Assumptions / Notes**
- Reset URLs contain identifiable token parameters that can be altered for testing.  
- The system does not leak internal error stack traces or sensitive information when encountering invalid tokens.

### TC-13 – Password reset link access by non-authenticated vs authenticated user

- **ID:** TC-13  
- **Title:** Password reset link access by non-authenticated vs authenticated user  
- **Linked AC:** User can set a new password via the reset link  
- **Type:** edge  
- **Priority:** low  

**Preconditions**  
User has a valid reset link and can log into the account using existing credentials as a separate test.

**Test Data**  
- Valid reset link  
- Valid login credentials for the user

**Steps**
1. Ensure you are logged out of the application (clear any active sessions).
2. Open the password reset email and click the valid link while not logged in.
3. Observe whether a password reset screen is displayed.
4. Now log into the application in a separate browser or session using the user's current credentials.
5. While logged in, open the same reset link again (either in same or different browser tab, depending on system behavior).
6. Observe any difference in behavior between authenticated and unauthenticated access to the reset link.

**Expected Result**
- The system consistently and securely handles reset link access, either requiring no prior login or properly validating token regardless of session state, without exposing additional user details or causing inconsistent behavior.

**Assumptions / Notes**
- System design regarding authenticated access to reset links is defined. This test checks for inconsistent or insecure behavior rather than enforcing a specific design.  
- Session management is functioning and can differentiate between logged-in and logged-out states.

> **Vagueness Flag:** Expected behavior is intentionally broad; refine with product/security once desired UX and security posture are finalized.

### TC-15 – Rate limiting or throttling on repeated reset requests

- **ID:** TC-15  
- **Title:** Rate limiting or throttling on repeated reset requests  
- **Linked AC:** User can request a reset link by entering their registered email  
- **Type:** edge  
- **Priority:** medium  

**Preconditions**  
Known or expected rate-limiting policy exists for password reset requests (e.g., max N requests per minute per IP or email).

**Test Data**  
- Registered email for repeated requests  
- Known/assumed rate limit configuration (if available)

**Steps**
1. Navigate to the application's login page.
2. Click "Forgot password" to access the password reset request form.
3. Enter a registered email address and click "Send reset link".
4. Immediately repeat the request multiple times (e.g., 10 requests) within a short period using the same email and from the same IP address.

**Assumptions / Notes**
- Rate limiting is part of the security requirements; if not implemented, this test may fail and should be treated as a security enhancement request.  
- Tester has ability to monitor email inbox to verify whether multiple reset emails are sent.

> **Vagueness Flag:** Multiple acceptable throttling behaviors are allowed; clarify exact UX and technical limits with security/product for precise expectations.
